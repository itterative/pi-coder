The agent MVP is implemented under `src/tools/agent/` and registered from `src/index.ts`. Run lifecycle events retain the execution `cwd` and include optional `parentCwd`, allowing the open `/agents` browser to refresh for isolated worktree runs while still scoping reloads to the parent project. The parent prompt uses an idempotent, session-cached `<delegated_agents>` block for available definitions; live run state is recovered through `agent(action="list")`, not injected into the system prompt. Runs now have optional persisted human-readable titles (or deterministic task-derived fallback titles), title-aware mailbox/worker/browser labels, and private per-transcript browser metadata sidecars; renaming remains deferred until the browser is productionized. `runs/manager.ts` owns the parent-runtime-local foreground/background run state machine; `child.ts` assembles controlled in-process SDK sessions from modules under `child/`; `definitions/discovery.ts` loads built-in, user, and trusted-project definitions. Source and tests use canonical module paths directly; the temporary root compatibility facades were removed. Tests are under `test/tools/agent*.test.ts`, including a real no-provider-call SDK construction smoke test. The evolving design and later phases remain in `src/tools/agent/PLAN.md`.

Behavior: ship a built-in read-only `scout`; custom user agents live in `~/.pi/agent/agents`, trusted-project agents in the nearest `.pi/agents`; built-in names are reserved; definitions sort by path and same-scope duplicates are first-wins with warnings; project agents override user agents with an informational diagnostic. One sequential parent `agent` tool exposes foreground `start`, asynchronous `spawn`, `status`, one-shot `collect`, `resume`, and `cancel`. Sequential spawn calls return immediately and may run up to four read-only children concurrently. A bounded `ctx.ui.setWidget(..., { placement: "aboveEditor" })` view shows running (`●`), waiting (`?`), ready (`✓`), and failed (`!`) live runs plus up to three terminal rows, with sanitized current tool activity and a short latest assistant-response preview; throttled child progress drives asynchronous updates. It clears entries on collection/cancellation. Do not also install a footer `setStatus` entry—the above-editor widget is the sole persistent agent UI. Background terminal children are disposed immediately while the latest 20 bounded results remain collectable; terminal results do not consume active capacity. A child-only `ask_parent` tool pauses the retained session for cooperative parent guidance, including background runs whose resume remains asynchronous. A restricted child-only `ask_user` reuses pi-coder's existing question component in TUI foreground mode and returns the answer to the same child turn; background children omit `ask_user` to avoid unsolicited parent-TUI dialogs. Cancellation is recoverable, parent abort/shutdown closes foreground dialogs, and non-TUI modes explicitly direct the child to `ask_parent`. Waiting is explicitly described as paused rather than completed; compact TUI results show the question/run ID or a final-result/status preview. Keep up to four starting/running/waiting/interrupted runs with no TTL; IDs become stale after collection/cancellation or bounded result eviction. Ephemeral parent runs also become stale on reload/replacement/restart, while persisted parents restore only within the exact original session and active tree branch; new/forked/cloned sessions do not inherit them. Diagnostics retain sanitized bounded timelines (latest 20 runs, 400 events/run) after terminal child disposal and register `/agent-trace` for list/inspect/explicit mode-0600 JSON save/clear. The intended final behavior remains opt-in via `PI_CODER_AGENT_TRACE=1`, but `isAgentTraceEnabled()` is temporarily hardcoded to `true` with a TODO while the extension is under development. The repeatable real-provider/lifecycle/confinement manual checklist is in `src/tools/agent/README.md`.

Safety/runtime constraints: child resources use `noExtensions: true` plus one explicit inline extension; all custom definitions remain under the `read`, `grep`, `find`, and `ls` ceiling. The built-in scout additionally has `bash`, but its child hook runs commands only when `getCwdConfinementAssessment()` returns exactly `SAFE_READONLY`; `SAFE_EDIT` and unsafe classifications are blocked without an approval bypass and expose a short explanation alongside their structured unsafe reason codes. `describeUnsafeReason()` owns the descriptions; diagnostics and returned assessments deduplicate reasons while retaining their first-seen order. Every path is confined to cwd with sensitive/symlink checks; parent abort calls `childSession.abort()`; agent instructions append to pi's base prompt; exact nested usage is aggregated and emitted as per-parent-call deltas. Model runtime setup preserves child-resolved OAuth, mirrors registered provider/native-provider configuration and resolved base URL/headers, and copies runtime API keys only for non-OAuth providers lacking child auth. Runtime-only unpersisted OAuth cannot be transferred through the public extension context and fails explicitly. An automatic non-interrupting parent mailbox is implemented in `presentation/mailbox.ts`: background waiting/terminal updates coalesce locally by run ID; markers are ephemeral and are not durably journaled or replayed after process restart, while durable run state/results restore independently. Active parent work defers flushing until `agent_settled`; an already-idle parent schedules an immediate microtask flush. One bounded hidden custom message is sent through `pi.sendMessage(..., { deliverAs: "followUp", triggerTurn: true })`, so active work is never steered or stopped but an automatic parent mailbox turn starts afterward. Full child output remains behind explicit `collect`. Spawn and background-resume outputs tell the parent not to poll `status`: automatic notifications arrive when a child finishes or needs parent guidance, after which terminal results are collected. `list` provides stable run-ID/status recovery after compaction or session restoration without injecting live run state into the parent system prompt; `status` remains an optional deliberate snapshot/recovery action. Reconciliation against `manager.listRuns()` drops markers made stale by resume, collection, cancellation, or result eviction, and shutdown clears pending updates. Automatic full-result delivery and explicit batch/chain syntax remain deferred. Manual real-provider testing confirmed automatic mailbox delivery works, though the user needed a full pi restart rather than `/reload`; investigate hot-reload behavior if reproducible. Before release, restore the intended opt-in trace gate. The mutation-capable worker MVP is implemented. One built-in same-checkout `worker` may run foreground or background with read/search/edit/write/bash; custom agents remain read-only and `worker` is reserved. Every child edit/write/bash requires a parent-visible run-labelled one-shot prompt. The prerequisite refactor is complete: bash session rules/mode and file-folder approvals are per-registration runtime closures, and `src/tui/dialog-queue.ts` provides one abort-aware FIFO queue shared by `askUser` and `selectWithMessage`; queued aborts return promptly without letting later dialogs overtake the active dialog. The worker gate in `src/tools/agent/child/worker-permissions.ts` uses `selectWithMessage(..., signal)` so parent and child permission dialogs share this queue. It serializes worker mutation calls through tool settlement, blocks outside/sensitive/symlink-escape paths before prompting, honors configured bash denial and sandbox/direct behavior, propagates user notes, and reports `waiting_for_permission` in the activity widget. Only one mutating child run may be active while scouts continue within the four-run bound, and that worker's mutation calls are serialized. Parent and worker activity can still mutate the shared checkout concurrently; attribution caveats remain explicit. Successful edit/write paths are retained in a terminal mutation report; approved bash adds an attribution caveat because bash and concurrent parent activity can change other files. Git-worktree isolation is implemented as a persistent user-managed workspace pool: an isolated worker selects the first ready workspace, an internal setup worker prepares a new one using permission-gated bash in the isolated worktree, and the requested task worker then runs there; setup is not exposed as an ordinary parent-model run. Setup bash defaults to a ten-minute timeout and must be non-interactive. Collecting a terminal isolated background run first finalizes its worker tree into a workspace result, attaches workspace/result IDs and revisions to the parent result, and leaves the parent checkout unchanged. No-change results create no durable ref and release the lease immediately; changed results retain a durable ref and lease until explicit disposition/application. `/agents` now provides direct workspace actions and an inline diff viewer inside the workspace details view for apply, retain, reset/reuse, and discard, with confirmations for destructive actions. Its visible overlay uses the reusable `src/tui/overlay-stack.ts` focus stack to retain keyboard focus over nested non-overlay custom components via pi TUI overlay handles/input listeners. The stack remembers the most recent component it displaced and restores that component after the last overlay closes. Participating overlays must register with the stack; unregistered simultaneous overlays remain an acknowledged edge case.

Durable paused/interrupted child sessions are implemented; arbitrary continuation of completed conversations remains deferred. Persisted parents use SDK `SessionManager.create/open` with child JSONL under `<pi-coder-install>/.state/agent-sessions/--<encoded-cwd>--/<parent-session-id>/`, plus versioned append-only parent custom-entry state. `PI_CODER_EXTENSION_DIR` is derived from `import.meta.url`; `normalizeCwdForSessionDirectory()` is consumed by `src/tools/agent/runs/persistence.ts` to centrally supply the pi-style cwd layer, the agent-session storage directories are mode 0700, and `.state/` is gitignored. `/agent-sessions` opens an overlay with Current and Past tabs, scanning active manager runs plus persisted child transcripts for the current cwd. Details render the active conversation's user/custom/assistant messages and compact tool calls; failed calls use `×`, edit calls show `-`/`+` lines, bash calls show their command, and consecutive tool-only responses have no blank rows. Model thinking and potentially large tool-result output are intentionally omitted. Details remain read-only, while `r` explicitly resumes interrupted current runs and `c` cancels waiting/interrupted current runs without automatic replay or resume. Only records bound to the exact parent session UUID and active branch restore: reload/restart/switch-away-and-back restore, while ephemeral parents/new/fork/clone do not inherit runs. Waiting children reopen paused, uncollected terminal outcomes restore from bounded parent metadata, and cleanly aborted or crash-stale active runs restore as `interrupted` and require explicit guidance. Mutations never auto-replay; unmatched crash-time tool calls receive synthetic uncertain-outcome errors before continuation. Current agent definitions/fingerprints are revalidated and mutation authority is derived only from the current reserved built-in worker. Usage checkpoints, active/terminal bounds, mutation reports, tree-branch rebuilding, and mailbox reconciliation are preserved. `/tree` is blocked while a child is actively streaming or waiting for permission; paused/interrupted/terminal runs can switch branches safely. Collection/cancellation/eviction append tombstones but retain child files so `/agent-sessions` can browse past work; a future prune policy will handle old transcripts and orphan directories after external parent-session deletion. See Phase 8 of `src/tools/agent/PLAN.md` and the durable-session section in `src/tools/agent/README.md`.

Prompt guidance: the parent agent may use its own active built-in tools directly; delegation is optional. The agent tool's `promptGuidelines` are appended flat to pi's `Guidelines` section, so each bullet explicitly names `agent`; current capability details are kept in the delegated-agent prompt block and tool description. The agent package is organized by responsibility under `contracts/`, `definitions/`, `runs/`, `child/`, `storage/`, `workspaces/`, `presentation/`, and `observability/`. The registration function remains in top-level `index.ts`, which composes top-level `lifecycle.ts`, `browser.ts`, and `action-dispatch.ts` for extension state/hooks, `/agents` orchestration, and tool routing.

The post-MVP architecture review and implementation status are recorded in `src/tools/agent/REORGANIZATION-PLAN.md`. Contract cycles were removed, metadata/catalog ownership was separated, workspace and child concerns were decomposed, parent/TUI dispositions now share `workspaces/actions.ts`, and source/tests import canonical modules without compatibility facades. The former registration controller is split across top-level `index.ts`, `lifecycle.ts`, `browser.ts`, and `action-dispatch.ts`. `presentation/browser-models.ts` now projects session/workspace/Git/action state so TUI browser components no longer depend on workspace, storage, or run-domain modules.
