The agent MVP is implemented under `src/tools/agent/` and registered from `src/index.ts`. `runtime.ts` owns the parent-runtime-local foreground/background run state machine; `child.ts` creates controlled in-process SDK sessions; `discovery.ts` loads built-in, user, and trusted-project definitions. Tests are under `test/tools/agent*.test.ts`, including a real no-provider-call SDK construction smoke test. The evolving design and later phases remain in `src/tools/agent/PLAN.md`.

Behavior: ship a built-in read-only `scout`; custom user agents live in `~/.pi/agent/agents`, trusted-project agents in the nearest `.pi/agents`; built-in names are reserved; definitions sort by path and same-scope duplicates are first-wins with warnings; project agents override user agents with an informational diagnostic. One sequential parent `agent` tool exposes foreground `start`, asynchronous `spawn`, `status`, one-shot `collect`, `resume`, and `cancel`. Sequential spawn calls return immediately and may run up to four read-only children concurrently. A bounded `ctx.ui.setWidget(..., { placement: "aboveEditor" })` view shows running (`●`), waiting (`?`), ready (`✓`), and failed (`!`) live runs plus up to three terminal rows, with sanitized current tool activity and a short latest assistant-response preview; throttled child progress drives asynchronous updates. It clears entries on collection/cancellation. Do not also install a footer `setStatus` entry—the above-editor widget is the sole persistent agent UI. Background terminal children are disposed immediately while the latest 20 bounded results remain collectable; terminal results do not consume active capacity. A child-only `ask_parent` tool pauses the retained session for cooperative parent guidance, including background runs whose resume remains asynchronous. A restricted child-only `ask_user` reuses pi-coder's existing question component in TUI foreground mode and returns the answer to the same child turn; background children omit `ask_user` to avoid unsolicited parent-TUI dialogs. Cancellation is recoverable, parent abort/shutdown closes foreground dialogs, and non-TUI modes explicitly direct the child to `ask_parent`. Waiting is explicitly described as paused rather than completed; compact TUI results show the question/run ID or a final-result/status preview. Keep up to four parent-runtime-local starting/running/waiting runs with no TTL; IDs become stale after collection/cancellation, bounded result eviction, reload, fork/session replacement, or restart. Diagnostics retain sanitized bounded timelines (latest 20 runs, 400 events/run) after terminal child disposal and register `/agent-trace` for list/inspect/explicit mode-0600 JSON save/clear. The intended final behavior remains opt-in via `PI_CODER_AGENT_TRACE=1`, but `isAgentTraceEnabled()` is temporarily hardcoded to `true` with a TODO while the extension is under development. The repeatable real-provider/lifecycle/confinement manual checklist is in `src/tools/agent/README.md`.

Safety/runtime constraints: child resources use `noExtensions: true` plus one explicit inline extension; all custom definitions remain under the `read`, `grep`, `find`, and `ls` ceiling; every path is confined to cwd with sensitive/symlink checks; parent abort calls `childSession.abort()`; agent instructions append to pi's base prompt; exact nested usage is aggregated and emitted as per-parent-call deltas. Model runtime setup preserves child-resolved OAuth, mirrors registered provider/native-provider configuration and resolved base URL/headers, and copies runtime API keys only for non-OAuth providers lacking child auth. Runtime-only unpersisted OAuth cannot be transferred through the public extension context and fails explicitly. An automatic non-interrupting parent mailbox is implemented in `mailbox.ts`: background waiting/terminal updates coalesce locally by run ID. Active parent work defers flushing until `agent_settled`; an already-idle parent schedules an immediate microtask flush. One bounded hidden custom message is sent through `pi.sendMessage(..., { deliverAs: "followUp", triggerTurn: true })`, so active work is never steered or stopped but an automatic parent mailbox turn starts afterward. Full child output remains behind explicit `collect`. Spawn and background-resume outputs tell the parent not to poll `status`: automatic notifications arrive when a child finishes or needs parent guidance, after which terminal results are collected. `status` remains an optional deliberate snapshot/recovery action. Reconciliation against `manager.listRuns()` drops markers made stale by resume, collection, cancellation, or result eviction, and shutdown clears pending updates. Automatic full-result delivery and explicit batch/chain syntax remain deferred. Manual real-provider testing confirmed automatic mailbox delivery works, though the user needed a full pi restart rather than `/reload`; investigate hot-reload behavior if reproducible. Before release, restore the intended opt-in trace gate. The mutation-capable worker MVP is implemented. One built-in same-checkout `worker` may run foreground or background with read/search/edit/write/bash; custom agents remain read-only and `worker` is reserved. Every child edit/write/bash requires a parent-visible run-labelled one-shot prompt. The prerequisite refactor is complete: bash session rules/mode and file-folder approvals are per-registration runtime closures, and `src/tui/dialog-queue.ts` provides one abort-aware FIFO queue shared by `askUser` and `selectWithMessage`; queued aborts return promptly without letting later dialogs overtake the active dialog. The worker gate in `src/tools/agent/worker.ts` uses `selectWithMessage(..., signal)` so parent and child permission dialogs share this queue. It serializes worker mutation calls through tool settlement, blocks outside/sensitive/symlink-escape paths before prompting, honors configured bash denial and sandbox/direct behavior, propagates user notes, and reports `waiting_for_permission` in the activity widget. Only one mutating run may be active while scouts continue within the four-run bound. Successful edit/write paths are retained in a terminal mutation report; approved bash adds an attribution caveat because bash and concurrent parent activity can change other files. Git-worktree isolation remains a future option.
