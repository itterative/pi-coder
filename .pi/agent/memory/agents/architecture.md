# Agent architecture

## Ownership

- `src/index.ts` registers the feature. The package is organized into `contracts/`, `definitions/`, `runs/`, `child/`, `storage/`, `workspaces/`, `presentation/`, and `observability/`.
- Top-level `lifecycle.ts`, `browser.ts`, and `action-dispatch.ts` own extension hooks/state, `/agents` orchestration, and parent action routing. `action-dispatch.ts` keeps `executeAgentAction` as the ordered façade — validate, route through a `switch` over the validated `AgentRequest` union, unwind a failed start's `StartTransaction`, then link any collected workspace result — with one named handler per action beneath it; `isAgentTerminalStatus` is the only terminal-status policy, so no handler re-lists statuses. Dispatch-level invariants (rejection before any workspace claim, lease transfer before the run exists, collect ordering, rollback paths) are characterized in `test/tools/agent-action-dispatch.test.ts`. `presentation/browser-models.ts` projects authoritative session/workspace/Git state for the TUI. Intra-agent helpers retain their data/action subject positionally and name ancillary dependencies/options—for example, event emission takes the event plus `{ sink, cwd }`.
- `runs/manager.ts` remains the stable public lifecycle façade and composition root. Its internal collaborators are `runs/run-state.ts` (mutable `AgentRun` representation with per-field ownership notes, shared limits, and run policy helpers: `RUN_DEFAULT_FLAGS`, `countActiveRuns`, `mutationRunsConflict`, `deriveAgentTitle`, `truncate`, `emptyProgress`), `runs/projection.ts` (usage/progress/details/outcome/summary/waiting-content projections), `runs/registry.ts` (in-memory registry, ID allocation, terminal retention), `runs/checkpoint-store.ts` (durable record projection, cache, and per-run write ordering), `runs/continuation-lease.ts` (lease grant, recovery wait, release, and loss-induced abort), `runs/child-setup.ts` (`createChildFactoryContext`, the child→run callback bridge with its hooks object), and `runs/restore.ts` (`AgentRunRestoreCoordinator`, chronological restoration eligibility). Collaborators must not import the manager; they receive dependency callbacks or an explicit hooks object. The manager keeps the ordered policy it cannot delegate: prompt driving and interruption precedence, terminal finalization and background retention, `removeRun` removal ordering, and the shutdown interrupt/await/settle phases. Those stay colocated and are documented in place; extraction is only warranted when an ordered transition can move without obscuring itself.
- Source and tests should import canonical modules directly; compatibility facades are intentionally removed.
- Durable-write diagnostics: `AgentRunPersistence.save` intentionally returns only a boolean, so `loadAgentRunPersistence` accepts `{ onRefusedWrite }` and reports every authoritative-snapshot refusal (never budgeted); `AgentLifecycle` records it as the `persistence.save_refused` trace event carrying the storage reason. Do not use `ui.notify` as a diagnostics channel for tests or callers — that warning is deliberately one per session for the human, and catalog-row losses stay invisible because the catalog is an explicitly lossy projection. Endgame (recorded in `src/tools/agent/PLAN.md`): publish on the agent event bus and centralize tracing so `AgentTraceStore` is not threaded by hand, since `AgentTraceStore.record` is a no-op once a run's trace is pruned.

## Definitions

- Built-ins: read-only `scout`, `reviewer`, and opt-in `advisor`, plus permission-gated `worker`; reviewer and worker include `memories` and `scratchpad`, while read-only scout and advisor include `memories` only. Foreground direct-user interaction is policy-controlled; the advisor is explicitly parent-guidance-only.
- Custom Markdown definitions are loaded from `~/.pi/agent/agents` and the nearest trusted `.pi/agents`. Definitions named `scout`, `reviewer`, `advisor`, or `worker` overlay matching built-in metadata but cannot change capabilities; empty bodies preserve the built-in role. `advisor` is disabled by default and is only exposed when enabled in agent configuration; files sort by path; same-scope duplicates are first-wins with warnings; trusted-project definitions override user definitions with an informational diagnostic.
- Every custom agent receives baseline `read`, `grep`, `find`, and `ls`. Optional capabilities include `memories`, `scratchpad`, `todolist`, `safe-bash`, and `command-runner`, while `edit` is reserved for the built-in worker. Implications live in the declaration layer (`agentCapabilities` in `definitions/types.ts`): `command-runner` implies `safe-bash`, `todolist` implies `scratchpad`. They are deliberately _not_ restated in the child-side capability units, because the effective set is what the parent-facing catalog advertises and what the definition fingerprint hashes. The `memories` capability loads pi-coder's memory extension in the child session and adds `~/.pi/agent/memory` as an additional read root; definitions may also declare `additionalPaths` read roots and exact `safeBashCommands` patterns. Custom safe-Bash patterns extend the curated command set conservatively and retain path/shell safety checks. `scratchpad` creates a private temporary `/tmp` workspace in the child session. Legacy `tools` is ignored with a warning. A definition may specify `model`; otherwise it uses the parent model. A `todolist` capability is implemented in `src/modules/todolist/PLAN.md`; its common frontmatter/schema parser, prompt (including a canonical YAML example), capability wiring, write/edit validation hooks, Bash change guard, shared event-driven status widget section, session-entry TODO snapshots, and volatile worker progress are implemented. Each runtime initializes or restores its TODO document from the latest valid snapshot on the active session branch; Bash deletion of a valid TODO recreates the empty document and persists that state, while invalid content still rolls back. Scratchpad paths are recorded in non-LLM-visible session markers and reused across reload/session switches while the mode-0700 directory exists. Documentation and hardening remain.
- The parent prompt receives an idempotent, session-cached `<delegated_agents>` catalog with names, sources, capabilities, and descriptions, plus explicit guidance to make delegation tasks detailed, self-contained, and multiline when useful; changing advisor availability refreshes the catalog. Full durable run state lives in the extension-local SQLite metadata database, while live run state is recovered with `agent(action="list")`, not injected into the system prompt.
- Runtime context is typed as bounded `context.sections`, deduplicated by ID and rendered into the initial task message rather than the system prompt. Every agent accepts the sections it is given: an absent policy, or one with empty `sectionIds`, accepts any ID under the renderer's default budget (`DEFAULT_CONTEXT_MAX_CHARS`), while a listed policy narrows the accepted IDs and sets `maxChars`; a non-positive or missing budget also falls back to the default. Only a policy that lists IDs can refuse an ID, so the parent-facing warning covers policy-refused and repeated IDs. The renderer bounds the complete context block, including headings and safety preamble. `contextPolicy` is not frontmatter-authorable, so only the built-in advisor narrows today. Changing a built-in policy value changes its `fingerprintAgentDefinition`, which invalidates durable continuation for runs persisted under the old fingerprint; `fingerprintLegacyAgentDefinition` exists only for the format that predates the field. Automatic parent-summary and recent-context collection is not implemented yet.
- The `agent` tool wire schema is deliberately a single flat object (required `action` enum plus all per-action fields optional, no anyOf/oneOf) so constrained-decoding engines such as llama.cpp can encode it as a grammar; `start` uses an optional `background` flag rather than a separate spawn action; do not re-introduce discriminated unions here. Per-action required/forbidden fields are enforced by `validateAgentParameters` in `definitions/validate.ts`, which throws `AgentActionError` with model-facing messages; dispatch narrows on the validated `AgentRequest` union, and `failedOutcome` must stay safe for partial params because validation errors flow through it.
- llama.cpp's grammar parser rejects any `char{m,n}` repetition where preceding-rule-count × n ≥ 2000 (`MAX_REPETITION_THRESHOLD`); n > 2000 is silently clamped to unbounded (constraint dropped), so bounded string maxLengths on nested positions (e.g. array-item strings in child `ask_user`/`ask_parent` options) must stay well under 2000 — keep them ≤ 1000. Symptoms: child session 400s with "Failed to initialize samplers: failed to parse grammar". Top-level string properties are rendered by the chat template as unbounded `xml-arg-string`, so their maxLength never reaches the grammar.

## Child runtime

- `createAgentChild` in `child/index.ts` is an ordered factory over named phases, each of which owns one invariant: `seedProgressTracker` (`child/progress.ts`) rebuilds a resumed run's tracker, taking authority data (changed/read files, `bashApproved`, `interrupted`) from the mutation report and display data from the progress frame; `resolveChildGrant` (`child/grant.ts`) is the single place a definition plus run mode plus parent UI becomes one `ChildGrant`, and it is the only place any of those decisions is made; `bootstrapChildSession` (`child/transcript.ts`) chooses open/materialize/in-memory and performs leaf selection **before anything reads the session context**, because `SessionManager.open()` positions on the newest physical leaf (it differs from `openPersistedChildSession`, which the session browser uses read-only without dir/cwd); `restoreChildSessionModel` (`child/model-runtime.ts`) reads the model and thinking level the transcript itself recorded so a continuation stays consistent with its own history; `createChildHandle` (`child/handle.ts`) owns the idempotent `dispose`, the one-shot `takeParentQuestion`, and the captured-at-construction `sessionFile`. Keep `toolExecution = "sequential"` driven by the grant's `requiresSequentialToolExecution` at the factory call site with its SDK-preflight-deadlock comment, and keep the `bindExtensions` rollback (`unsubscribe()` then `session.dispose()` then rethrow) before the handle exists.
- Capability knowledge is layered, and the layer boundaries are the design: `definitions/types.ts` declares names, baseline, implications, and the authority ladder; `child/capabilities/` holds one unit per capability owning its session tools, read roots, and registered extension (`capabilityTools`, `capabilityReadRoots`, `capabilityExtensions`), with **registry order load-bearing** because the tool allowlist is ordered and extension order decides handler order; `child/gates/` holds one file per authorization surface with an optional `applies` and its own `install`; `child/prompt/` holds the four run-mode profiles and the shared sentences. `registerChildExtension` now only builds the shared gate runtime and calls `installChildGates`. Adding a capability means adding a unit and the declaration name, not a new boolean on the grant or a new flag combination at a call site.
- The authority ladder (`read < inspect < command < mutate`) orders **gate strength only**: which gates apply, whether calls serialize, and which extension label a child carries. Tool presence is a separate question answered by the units, because `edit` does not imply shell access — an edit-without-`command-runner` definition must get no `bash` tool. This distinction was found by the restructure's differential oracle after a rung comparison silently widened tool access; do not reintroduce `hasAgentAuthority(authority, "inspect")` as a tool-presence test.
- Gate installation order is behavior, not style: bash-output, file-access, interaction, commands, confinement. pi runs `tool_call` handlers in registration order, the file-access gate records approvals that the command and confinement gates then honour via `isFileAccessApproved`, and the confinement handler runs last so a Bash call reaching it means no command gate claimed it (below the `command` rung the heuristic guard is the _only_ bash control). `test/tools/agent-child-gates.test.ts` pins the ordered registration record; `test/tools/agent-child-decisions.test.ts` pins the allow/block truth table with its reasons.
- The gate runtime resolves two permission-state handles that must not be merged. `parentPermissionState` is deliberately computed **without regard to isolation**, because an explicitly remembered Bash rule in an isolated child is written back into the parent session; `permissionState` is what the child may _read_, defined for exactly a non-isolated child whose parent has a session and whose rung is `command` or above. Gates test `permissionState` presence rather than re-testing isolation (`child/gates/runtime.ts` records the iff), and the fold is asserted in `agent-child-gates.test.ts`. A worker whose parent has no session therefore behaves like an isolated one for path prompts.
- Two small shared leaves exist because their duplication was drift-prone: `child/roots.ts` (`scratchpadRoots`, previously copied in the extension and the command gate) and `child/policy.ts` (`CHILD_CONFINEMENT`, previously three copies across the heuristic guard, the read-path guard, and the command gate under a different name). Confinement policy must stay one object; the `access: "read" | "write"` argument at each call site is the only axis the guards legitimately differ on.
- `presentation/outcomes.ts` derives catalog-only blocker rows from workspace state and renders the `list` outcome in the same module. Keep the `WorkspaceBlocker.result` / `blockingResult` split: the raw latest result decides a row's status and the `workspace-registry` label, while only a prepared result (or any result under `review_required`) holds the workspace open and earns a row, so the two must not collapse into one field. `blockedRunIds` falls back to `workspace-<id>` whenever nothing else named a subject, which is why a vanished worktree with a released result renders a `worker` row under a registry id; `blockedRunGuidance` is workspace-level, so a lease row and a result row in the same workspace print the same instruction. Both asymmetries are pre-existing and pinned by `test/tools/agent-outcomes.test.ts` snapshots; changing either is a behavior decision, not a cleanup.
- `isolated` is resolved once, in the grant: `context.isolated === true || context.workspaceId !== undefined`, because a restored isolated run keeps its workspace id when the transient flag was not persisted. The protocol prompt and the gates both consume that single value. (Before the grant existed, the prompt reconciled it and the extension received the raw flag and reconciled it again internally, with a comment asking future readers to keep the two spellings in step.)
- `canAskUser` also resolves once, in the grant: the definition's `allowUserInteraction` is necessary but not sufficient — the parent must have a UI _and_ be in TUI mode. The child extension receives the resolved flag and must not re-derive it.
- `snapshotProgress` (`child/progress.ts`) is the single progress-frame projection for the parent callback, the child extension's permission frame, and the handle's `getProgress`; three hand-inlined copies had already begun to differ in where they read `permissionPending`. That field is what `runs/child-setup.ts` turns into `waiting_for_permission`, so the frame shape is asserted with `toStrictEqual` in `test/tools/agent-child-progress.test.ts` rather than inferred from a render.

- Child sessions use `noExtensions: true` plus an explicit child extension, avoiding recursive pi-coder loading while retaining child-specific hooks such as confinement and `ask_parent`. Agents with the `memories` capability additionally receive the pi-coder memory extension and its user-memory read root; agents with `scratchpad` receive the temporary scratchpad extension.
- Agent instructions are rendered as stable role plus protocol layers inside `<delegated_agent_instructions>` XML blocks appended to Pi's base prompt. The wrapper explains that the blocks define the child role and operating protocol. Protocol wording is written from the delegated agent's perspective: describe whether a tool call runs, pauses for end-user approval, or is blocked; keep UI concepts such as parent-visible permission prompts out of child instructions. The protocol is composed from one of four run-mode profiles in `child/prompt/` rather than a flag-driven branch chain, and full rendered prompts are file-snapshot tested for every built-in role and each distinct worker run mode, including same-checkout and isolated worktree, always through `resolveChildGrant`. Runtime context is rendered separately into the initial task message. Runtime factories keep provider/model setup isolated per run and bridge parent aborts to `childSession.abort()`.
- A child is never told whether it runs in the background: the prompt has no background input, and a background parent (no UI, print mode) produces the same protocol text as a definition that declines direct interaction. `background` still reaches the parent-facing guidance and traces; do not add a child-facing background paragraph without deciding what it should say, and keep `test/tools/agent-prompt.test.ts` asserting the no-UI/declined equivalence rather than snapshotting a duplicate of the scout prompt.
- Child model setup preserves child-resolved OAuth, mirrors registered provider/native-provider configuration and resolved base URL/headers, and copies runtime API keys only for non-OAuth providers lacking child auth. Runtime-only OAuth cannot be transferred through the public extension API and must fail explicitly.
- Non-isolated children share the parent session manager's live Bash permission state. Non-isolated workers additionally inherit read/write folder approvals for explicit outside-cwd access; same-checkout worker edits inside cwd are allowed directly. Isolated task workers' direct edits inside their dedicated worktree are also allowed directly, while isolated task/setup workers receive separate Bash permission state and prompts. Children with Bash access can read exact validated temp files exposed as truncated Bash full-output paths; this read-only exception is rehydrated from the child transcript when possible and never broadens Bash or write access.
- Exact nested usage is accumulated from child messages and returned as a delta on each parent-visible start/continue/status result; cumulative usage remains for display.

Tests include no-provider-call child SDK construction and orchestration coverage under `test/tools/agent*.test.ts`. Real provider, lifecycle, and rendering checks remain in `src/tools/agent/README.md`.
