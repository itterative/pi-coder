# Testing pi-coder

Run the full suite with `npm run test:run` and check types with `npm run typecheck` (or `npx tsc --noEmit`). The tests cover the consolidated TUI, memory, config, and sandbox modules.

## Checklist before adding or changing a test

- **Reuse a double before writing one.** See `test-doubles` for the catalog: `createPiStub`/`stubContext` for the `pi` surfaces, `agent-doubles` `partial*` for domain objects, `child-run-fixture` for a wired child extension, `test/helpers.ts` for TUI driving, `e2e/helpers.ts` for temp dirs/SQLite/git. A hand-built `const pi = { ... } as any` is the pattern that produced 28 duplicates and 199 `any` findings; the cleanup that removed them finished with the TUI/dialog cluster, so `no-explicit-any` is now zero repo-wide and any new hit is a regression rather than baseline noise.
- **No new `no-explicit-any`.** Where a signature genuinely cannot be implemented from test code, cast to the _real_ type and state the reason in place (see the narrowing policy in `test-doubles`). `npx eslint test/<file>` must be clean on files you touched before you call the work done.
- **Assert a behavior, not a wiring detail.** A test that restates a literal (`expect(x.hardcodedField).toBe("same")`) catches nothing; test a double's ordering and failure contracts, not its field copying.
- **Typecheck the test file too**, since `tsconfig.json` excludes `test/` — `npm run typecheck:tests` (config `tsconfig.check.json`) compiles `src` plus `test` under the project's real options and is wired into `npm run check`; for one file use `npx tsc --noEmit --strict --target ES2022 --module ESNext --moduleResolution bundler --skipLibCheck --types node,vitest/globals test/<file>.test.ts`.
- **Run the touched suite even when typechecking passes** (see the paragraph below on `TypeError: cloneUsage is not a function`).
- **Rendering: distinct states via file snapshots**, `snapshotText(...)` + `toMatchFileSnapshot(...)`, plus direct state or interaction assertions; keep clocks, temp dirs, repo paths, and sandbox argument lists normalized out of snapshots.
- **State stays out of the repo**: explicit temporary state/workspaces directories; never mutate `.state/`.
- **Verify any code you hand to a child.** When a delegation task quotes a helper signature or a snippet, run the single-file probe over it first and say where reality was measured (commit, line numbers). A child cannot tell an illustrative sketch from a checked example, so an unverified snippet costs a round trip when the child reports the mismatch — or gets quietly worked around.
- **Prettier only on explicit file paths, at the end**, then check `git status` for collateral `*.md` reformatting.

Quality checks are available through `npm run lint`, `npm run format:check`, and `npm run knip`; `npm run check` runs typechecking, linting, formatting, tests, and Knip together. ESLint uses the flat config in `eslint.config.mjs`, with cyclomatic and cognitive complexity currently reported as warnings. The repository currently has pre-existing lint, formatting, and Knip findings; do not treat those baseline findings as regressions without comparing changes.

Use `./scripts/cognitive_load_report.py` for a detailed complexity overview. It runs ESLint once, tolerates unrelated lint errors, reports both complexity rules plus a function-size and nesting tree, groups findings by file/subsystem, and supports `--target`, `--top`, `--format json`, `--input`, `--min-function-lines`, `--big-function-lines`, `--child-function-lines`, `--no-structure`, and threshold options. The size pass injects `max-lines-per-function` through `--rule` in the same ESLint run, nests reported spans, and separates a function's own lines from its children's; rank by self lines to find undecomposed bodies, and by span with a high nested count to find behavior assembled across callbacks. `--input` skips the size pass unless that saved report already contains the rule. Keep those two floors distinct: ESLint's rule threshold is the _measurement_ floor (`INVENTORY_FUNCTION_LINES`) and must stay low, because a function that is never reported cannot be subtracted from its parent's self count, so raising it makes a function that already delegates read as one undecomposed body; `--min-function-lines` is only the _display_ floor and defaults to two thirds of `--big-function-lines`.

Use `./scripts/coverage_report.py <source-glob> --tests <files...>` to see which paths a suite never reaches before refactoring, since coverage percentages alone hide that. It runs `vitest run --coverage` scoped to the targets (or analyzes an existing `coverage-final.json` with `--input`) and lists each uncovered branch _path_ with its own source line, plus uncovered statements and functions, and supports `--top`, `--format json`, and `--fail-on gaps|thin --min-branches`. Narrow `--tests` deliberately: Vitest instruments only what the selected tests load, so untargeted files report as never loaded.

For a manual permission-prompt check, run `cat /etc/hostname`; without a matching rule it should prompt with `ask`. Verify the `selectWithMessage` UI, long-command wrapping and scrolling, Tab edit mode, bracketed clipboard paste, wrapped feedback, and Enter/Escape behavior.

Database-backed agent tests must use an explicit temporary state/workspaces directory; integration tests that only exercise agent action presentation should mock catalog access rather than allowing the default `.state/meta.sqlite` path. The project-local `.state/` directory is runtime state and must not be mutated by the test suite. Shared workspace lifecycle E2E tests live under `test/tools/e2e/` and should use its `createE2EPaths`, `createE2EContext`, `withE2EMetadataDatabase`, and `createScriptedChild` helpers so temporary SQLite, context defaults, cleanup, and child handles remain consistent. `createE2EContext` now returns a typed `AgentStartContext` and deliberately carries no `ui` (the start context has no such member), so a checked parent context is `stubContext`/`stubSessionContext` while an e2e run context is `createE2EContext`. Drift still open: `e2e/helpers.ts` carries its own `zeroUsage()`; prefer the `agent-doubles` version in new code.

TUI widget tests must assert distinct projected **states**, not a trace of render frames. The background-flow recorder in `test/tools/agent-tool.test.ts` dedupes consecutive identical frames before `toMatchFileSnapshot`, because the widget requests a render on every status event, so a raw frame trace snapshots how many microtask boundaries a flow contains and a transient state (`Starting:`) can coalesce into the next frame. Keep that recorder dedupe when adding widget coverage, and prefer `vi.waitFor` over fixed flush counts for background-settling assertions.

Typechecking does not cover tests by default: `tsconfig.json` includes only `src/**/*.ts`, so a bare `npx tsc --noEmit` stays green after a test imports a name the module no longer exports, and the only symptom is `TypeError: cloneUsage is not a function` when Vitest runs it. `import type` is the quieter variant of the same hole: a type imported from a module that never exported it erases at runtime, so the suite passes and only the single-file probe reports it. Always run the touched suite after a structural change even when typechecking passes, and run the probe to catch the type-side drift. The project-wide variant is now a gate, which is also what catches a test leaning on runtime API beyond the compile target — `Array.prototype.findLast` is ES2023 and this project targets ES2022, so it runs in Node yet must not be used in tests. `test/helpers.ts` `interact()` binds `component.handleInput` once and throws a named error when a component implements none, because pi types that member optional and `?.()` would silently drop keystrokes from a TUI flow.

For text a module renders for a model or user to read (agent list rows, outcome envelopes, transcripts), characterize with one sectioned file snapshot per group instead of fragment `toContain` assertions: join `### case` blocks, normalize the clock out through a `stableDetails`-style helper, and write the file with `snapshotText(...)` plus `toMatchFileSnapshot("__snapshots__/...")`. Generate it from the pre-change code so it pins reality rather than aspiration. In `presentation/outcomes.ts` the seven existing fragment tests caught 3 of 13 mutations; the snapshot suite caught 15 of 15 and exposed two real inconsistencies in the same pass.

To prove a pure or near-pure module survived a restructure, copy the pre-change file out of git next to the new one (`outcomes-baseline.ts`), write a temporary differential test comparing rendered output over a generated input matrix, then delete both files. Include a negative control: mutate one asymmetric rule in the new module and confirm the differential test fails, otherwise an accidentally identical import pair reads as a proof. Compare **in the same process** rather than against a golden JSON file captured earlier: a file-based oracle inherits ambient state (config singletons initialized differently in a solo run versus a full-suite worker, `git config` lookups, `bwrap` availability) and reports order-dependent mismatches that are not behavior changes. Three hazards when the subject installs event handlers: handlers legitimately mutate their input (the command gate rewrites `input.command` when sandboxing, the mutation gate writes `_userMessage`), so rebuild the call corpus per implementation or the first side poisons the second; a mutation lock is held until `tool_result` arrives, so a driver that never sends one deadlocks; and driving a handler against a parent that reports a UI reaches a real dialog that can never resolve in a test, so use the no-UI arm where every prompt denies deterministically. Freeze the _whole_ decision chain: a copy of `child/` that still imports the live `definitions/types.ts` cannot see a change to capability semantics, which is how the differential missed its first real over-grant.

Prettier must be run on explicit file paths, never a directory: `npx prettier --write src/tools/agent/` sweeps the `*.md` files under that directory into a reformat — including `src/tools/agent/TODOS.md`, which is user-managed — and `npm run format:check` will not flag it because those paths are outside the sanctioned glob, so the damage only appears in `git status`. Check `git status` after any `--write` before reporting a task clean.

When proving a test actually detects a regression, mutate the source and confirm the test fails—and assert the mutation applied. An exact string replace silently becomes a no-op when formatting differs (Prettier re-wraps long boolean expressions), which reads as “the tests caught nothing” and can also leave the tree mutated: restore from a saved copy, not by re-running the reverse replacement. Verify the mutation was actually written before running the suite, because re-testing an untouched file looks identical to an undetected regression.

When an applied mutation genuinely produces no failures, diagnose the clause before adding tests: it is often already redundant, because a helper enforces part of the condition. That is what happened with `finite(value) && value < 0` in `runs/persistence/stored-record.ts`, where `finite` also rejected negatives. Fix the naming rather than doubling down—the helper is now `nonNegativeNumber`, whose name carries the whole contract—then pin the boundary with a case per direction (negative timestamps and a negative failed-tool count in `test/tools/agent-run-snapshot-shape.test.ts`) so a future relaxation of the helper is caught at the call sites that matter. Second, check whether the mutant is _equivalent_ before writing a test for it: `previous.order <= entry.order` and `< entry.order` in `runs/persistence/load.ts` cannot disagree, because markers arrive in ascending transcript order, so only the newest can win either way; reversing the comparison to `>=` is caught by the existing branch-checkpoint test. Prove equivalence by mutating in the direction that must fail before concluding a behavior is unguarded.

Child-side tests build a real grant instead of an internal option bag: `test/tools/child-run-fixture.ts` resolves through `resolveChildGrant` and installs the child extension against a recording `pi`, so a fixture cannot drift from what `createAgentChild` does. Two suites replace the old hand-written bags: `agent-child-gates.test.ts` pins the ordered registration record per profile (which gates a child arms, and that `ask_user` appears only when the parent can host it), and `agent-child-decisions.test.ts` snapshots the allow/block truth table with its reasons plus the tracked change sets. Keep path- and machine-specific noise out of those snapshots: normalize the per-run temp directory, the repo path, the home directory, and the entire bubblewrap argument list (a sandboxed command reads as `sandbox(<inner command>)`), and send `tool_result` only for calls that were allowed, otherwise the snapshot claims edits that never happened. When a behavior test needs a note recorded before a side effect, drive the callback directly rather than through a real extension.

A test that hand-writes an internal option bag can pass while describing a child that cannot exist: the per-built-in prompt snapshots passed `additionalPaths: []`, so they omitted the `", or configured additional paths"` clause that memory-capable agents really get, and the worker cases hid that by not using the read scope. Snapshot wording changed only after the fixtures resolved for real, which is the point. When converting such tests, expect to review the diff per agent and confirm the substance is unchanged. Related: when a test claims to pin a _distinct_ case, compare its snapshot against the nearest sibling (`cmp`); `agent-prompt.scout-background.system.txt` was byte-identical to the scout file because the prompt never read `background` at all, so the case pinned nothing. Replace that pattern with an equality assertion that states the real invariant.

Agent definition tests copy real `.md` fixtures from `test/tools/fixtures/agent-definitions/` into a temporary scope via `copyFixtures`, rather than inlining frontmatter strings: the loader's contract is about the files it reads, so sort order picks the duplicate that wins and each diagnostic reports the offending path. Keep new malformed-field cases as one fixture per guard and assert message plus paths together, which is what pins guard order. Reuse the fixture directories already next to a suite (`agent-transcripts/`, `agent-definitions/`) and resolve them with `fileURLToPath(new URL(..., import.meta.url))`.

Loader tests must build records with the real `parent.getSessionId()`. `validateAgentRunSnapshot` compares the stored owner against the session's id, so a fixture owner (the `"parent-1"` used by the fake `context()` in `test/tools/agent-persistence.test.ts`) is rejected, and the only symptom is the generic “parent marker and SQLite snapshot identity do not match” diagnostic, which looks like a validator defect. Instrument `listAgentRunSnapshotsInDatabase` plus `validateAgentRunSnapshot` directly before chasing such a message: a real `SessionManager.create` used as `sessionManager` supplies `getEntries`/`appendCustomEntry`, so `hasEntryIndex` is true and the marker/expectation paths behave as in production.

Parser benchmarks:

- `npm run bench` runs `test/modules/sandbox/bash.bench.ts`, measuring `parseBashAst()` across simple, medium, and high-complexity command corpora. Benchmarks are separate from `npm run test:run`.
- Benchmark output is machine-specific and intended as a future AST-parser performance baseline, not a hard threshold.

Relevant test locations:

- `test/ask-user.test.ts`, `test/select-with-message.test.ts`, and `test/inline-editor.test.ts` for TUI editing.
- `test/modules/memory/` for frontmatter parsing, memory scanning, and list formatting.
- `test/common/config.test.ts` and `test/modules/sandbox/` for sandbox behavior, heuristics, permissions, resolution, suggestions, bubblewrap, fuzzing, and bash parsing.
