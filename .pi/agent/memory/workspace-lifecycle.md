---
name: workspace-lifecycle
description: Workspace lease and collection invariants discovered during manual validation.
category: architecture
---

A no-change `workspace_results` row may outlive the lease that created it. Workspace `latestResult` is a display projection only: result actions resolve the exact run-instance/result row and reserve it with a compare-and-set token before side effects. Historical changed results use their immutable Git ref and must not reset a reused worker's worktree. Result reservations record the owner PID and can be reclaimed only after dead-owner verification and a grace period; reset/discard/recycling are serialized against active reservations. Reset, discard, and verified no-change release must rebase the reusable worktree and stored `base_revision` to the current parent HEAD; otherwise a later worker can run against stale source. Reconciliation must only release a task lease when `latestResult.runId === workspace.leaseRunId`; otherwise a new task lease can be released because of an older result. Collection must consume the retained agent result before releasing a no-change lease, so failed collection cannot strand an unleased retained run. Manual workspace collection flows must use `agent(action="start", background=true, isolation="worktree")`; foreground `start` results are returned directly and are not collectable. Foreground isolated `start`/`continue`/explicit cancellation must therefore prepare the workspace result directly, releasing verified no-change leases or retaining changed leases for disposition. `/agents` browsing runs the same safe no-change reconciliation; changed/uncertain leases remain protected. A lease with any matching catalog row is known, including terminal runs whose prepared result still awaits disposition; only a missing catalog row is orphaned. Parent agent actions can inspect, apply, discard, or continue prepared isolated results; continuation starts a new worker in the same leased workspace. Past persisted startup/running metadata is displayed as interrupted because no live child handle is attached to a past transcript. Workspace browser actions must compare both lease ownership and `latestResult.runId === leaseRunId`: apply/retain remain owner-bound, while reset/discard may manually clear an inactive task lease from another session. Durable active task leases and setup leases remain protected; orphan recovery remains available. A historical result must not suppress stale-lease release. Reset returns a freshly reloaded workspace row so cleared lease state and discarded-result status are projected immediately. Result application records an `applying` state before changing the parent; re-entry uses an owner/liveness check plus a CAS recovery claim so a live apply cannot be reinterpreted concurrently, while a crashed apply can be classified as applied, unapplied, or uncertain. Workspace allocation serializes its capacity check, worktree creation, and row insertion under a SQLite write transaction; new isolated work is conservatively rejected while the parent checkout is dirty.
